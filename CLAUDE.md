# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project purpose

Django web app to collect anonymous human evaluations of LLM outputs. Participants walk through a **PsyToolkit-style paged survey** answering quality + demographic questions about each stimulus. Stimuli can be audio clips, images, or text-only prompts (one `Stimulus` model with a `kind` discriminator). No login required for participants, multiple submissions allowed; each survey has a direct shareable link `/s/<slug>/` and there is no public index of active studies. webeval is **multi-user**: each study has an **owner** and is shared with collaborators by role (owner/editor/viewer); researchers work from a server-rendered **studio** dashboard at `/studio/` (the [accounts/](accounts/) + [studio/](studio/) apps), while staff/superusers use the Django admin (themed with django-unfold) to configure experiments. The `/admin/` index carries global summary cards and each Experiment change view embeds per-experiment stats with links into admin-mounted detail/CSV/chart views; the studio dashboard reuses those same stats/export functions. See [README.md](README.md) for the full product description.

## Tooling

- Package manager: `uv` (see [pyproject.toml](pyproject.toml), [uv.lock](uv.lock)). Python `>=3.11`. The project is non-packaged: `[tool.uv] package = false` tells uv there is no wheel to build.
- Install deps: `uv sync`
- Run everything through `uv run` so the project venv is used.

## Common commands

- Dev server: `uv run ./manage.py runserver`
- Migrations: `uv run ./manage.py makemigrations` / `uv run ./manage.py migrate`
- Create admin user: `uv run ./manage.py createsuperuser`
- Run full test suite: `uv run pytest`
- Fast path (skip browser-driven tests): `uv run pytest -m "not selenium"`
- Only the Selenium admin tests: `uv run pytest -m selenium`
- Focused test run: `uv run pytest -k <keyword>` or `uv run pytest path/to/test_file.py::TestCase::test_method`
- Coverage: `uv run pytest --cov=experiments --cov=survey`
- Migration drift check: `uv run ./manage.py makemigrations --check --dry-run`
- Purge one experiment's participant data: `uv run ./manage.py purge_experiment <slug> --yes`

Tests use `pytest-django` (configured in [pyproject.toml](pyproject.toml) under `[tool.pytest.ini_options]`) — do **not** use `./manage.py test`. An autouse `conftest.py` fixture redirects `MEDIA_ROOT` to a tmp dir so test uploads never hit the real `media/` directory.

## Architecture

Five Django apps sit as siblings of [core/](core/) (the project package):

- **[experiments/](experiments/)** — domain models, admin, and all staff-side stats/export surfaces. Owns `Experiment`, `Condition`, `Stimulus` (with `kind ∈ {audio, image, text}`), `Question` (with `page_break_before`), plus the pluggable assignment strategy ([experiments/assignment.py](experiments/assignment.py)), reproducibility-export builder ([experiments/exports.py](experiments/exports.py)), aggregate stats ([experiments/stats.py](experiments/stats.py)), SVG charts ([experiments/charts.py](experiments/charts.py)), and CSV exports ([experiments/csv_exports.py](experiments/csv_exports.py)). `ExperimentAdmin.get_urls()` mounts per-experiment detail/CSV/chart views under `/admin/experiments/experiment/<slug>/…`; the researcher-facing [studio/](studio/) dashboard reuses these same stats/export functions outside the admin.
- **[survey/](survey/)** — participant-facing flow. Owns `ParticipantSession` (with `current_assignment_index`, `current_page_index`, `demographic_page_index` cursors), `StimulusAssignment`, `Response`, the flow state machine + PsyToolkit pagination helpers ([survey/flow.py](survey/flow.py)), UA + GeoIP metadata capture ([survey/metadata.py](survey/metadata.py)), and the vanilla-JS audio tracker ([survey/static/survey/js/audio-tracker.js](survey/static/survey/js/audio-tracker.js)). Routes live at `/s/<slug>/…` (including a token-based `resume/<token>/` for save-and-continue-later: `ParticipantSession.resume_token` is a nullable-unique secret set at creation, and the resume view re-establishes the cookie and bounces to `required_step_url`); there is no landing page (`/` returns 404). Inactive experiments render `survey/templates/survey/unavailable.html` instead of 404ing.
- **[apikeys/](apikeys/)** — self-service, scoped, audited API keys for the staff REST API. Owns `APIKey` (SHA-256 hashed, per-user, rotatable, revocable, optional expiry) and `APIKeyEvent` (append-only audit log: `created`/`rotated`/`revoked`/`used`/`auth_failed`). Replaces `rest_framework.authtoken` entirely; the wire format stays `Authorization: Token <key>`. Scopes are declared in [apikeys/scopes.py](apikeys/scopes.py); views opt in with `permission_classes = [HasScope("<scope>")]` and inherit `LogAPIKeyUsageMixin` to record every call. Staff UI is mounted at `/admin/api-keys/` (templates in `apikeys/templates/admin/apikeys/`, URLs in [apikeys/admin_urls.py](apikeys/admin_urls.py)); superusers additionally have read-only changelists at `/admin/apikeys/apikey/` and `/admin/apikeys/apikeyevent/`.

- **[accounts/](accounts/)** — identity + access control. Owns `Profile` (1:1 `User`; we deliberately do **not** swap `AUTH_USER_MODEL`), `Membership` (per-study owner/editor/viewer role), `Invitation` (single-use, expiring, tokenised), and the append-only `AccessEvent` audit log. The single permission helper [accounts/permissions.py](accounts/permissions.py) backs every surface; write-side mutations + audit logging live in [accounts/services.py](accounts/services.py); the admin-scoping mixin is [accounts/admin_mixins.py](accounts/admin_mixins.py). Also owns the researcher auth views (login/logout/register/profile/invite-accept) at `/accounts/…` and Unfold-themed `UserAdmin`/`GroupAdmin`. `Membership`/`Invitation`/`AccessEvent` reference `experiments.Experiment` by **string** so `experiments` never imports `accounts` at module-load time (dependency direction stays `studio → accounts → experiments`).
- **[studio/](studio/)** — the researcher-facing dashboard at `/studio/…` (server-rendered, its own Pico.css base, model-free). Study list, creation, per-experiment overview (reuses the `experiments` stats/charts/csv/exports modules — no duplication), and the access-management page. Lives **outside** the Django admin and is usable by non-staff users. **Question authoring** is now native here via the drag-&-drop builder (`study_build` / `study_build_save`); conditions/stimuli authoring still happens in the (ownership-gated) admin and is linked out for staff.

The [core/](core/) package holds settings ([core/settings.py](core/settings.py)), URL wiring ([core/urls.py](core/urls.py)), and WSGI/ASGI entry points.

### Admin theme

The staff admin is themed with **[django-unfold](https://github.com/unfoldadmin/django-unfold)** (`django-unfold>=0.40,<1.0`). Four things make this work:

1. `"unfold"` and `"unfold.contrib.forms"` are prepended to `INSTALLED_APPS` **before** `"django.contrib.admin"` so Unfold's template overrides win the template search.
2. Every `ModelAdmin` / `TabularInline` in [experiments/admin.py](experiments/admin.py) and [survey/admin.py](survey/admin.py) inherits from `unfold.admin.ModelAdmin` / `unfold.admin.TabularInline` instead of the stock admin classes. All standard options (`list_display`, `fieldsets`, `inlines`, `form`, `actions`, `prepopulated_fields`) are inherited unchanged.
3. The `UNFOLD["SIDEBAR"]` dict in [core/settings.py](core/settings.py) uses `show_all_applications=False` and supplies a **curated navigation list** with three groups (Overview / Studies / Participants) and Material-Symbols icons. This is deliberate: without `show_all_applications=False` Unfold renders a second auto-generated "all apps" list below the curated one, producing two sidebars. Sidebar links use `reverse_lazy(...)` — plain `reverse()` crashes at settings import time because URLconf isn't loaded yet.
4. [templates/admin/index.html](templates/admin/index.html) extends Unfold's `admin/base.html` and adds a "summary cards" grid above the app list. The cards read from `webeval_summary` in the template context, which is populated by the [core/context_processors.py](core/context_processors.py) `admin_summary` processor — registered in `TEMPLATES[0]["OPTIONS"]["context_processors"]`. The processor short-circuits when the request isn't under `/admin/` or the user isn't staff, so it costs nothing on participant pages.

The Experiment changelist "Shortcuts" column ([experiments/admin.py](experiments/admin.py) `ExperimentAdmin.shortcuts`) renders a per-row link cluster (details page + JSON + printable export + participant survey link). Per-experiment stats live entirely inside the admin: `ExperimentAdmin.live_stats` is a readonly field on the change form, and `ExperimentAdmin.get_urls()` mounts four staff-only views under `/admin/experiments/experiment/<slug>/…` — `details/` (the Unfold-themed detail page at [experiments/templates/admin/experiments/experiment/details.html](experiments/templates/admin/experiments/experiment/details.html)), `answers.csv`, `demographics.csv`, and `chart/mean-ratings.svg`. Reverse names are `admin:experiments_experiment_details` / `_answers_csv` / `_demographics_csv` / `_chart_mean_ratings`.

Participant-facing survey pages are **not** themed with Unfold — they keep the Pico.css shell from [templates/base.html](templates/base.html) with a custom PsyToolkit-inspired layer on top (`.survey-header`, `.progress-bar`, stacked radio lists, narrow-column content). Unfold only touches staff pages.

### Key architectural invariants

- **Experiment lifecycle is draft → test → active → closed.** Structural edits (add/remove `Condition`, `Stimulus`, `Question`) are blocked once the experiment leaves draft. This is enforced in `experiments/models.py` via `_ensure_draft()` called from `clean()` **and** `delete()` of each child model, plus `_ALLOWED_TRANSITIONS` in `Experiment.clean()`. Admin inlines additionally use `_ReadOnlyWhenLockedMixin` so the UI reflects the lock. `_ensure_draft()` checks the parent's **committed** state (via a DB lookup), not the in-memory instance, because Django admin inlines re-validate every child row when the parent is being saved — reading the in-memory state would wrongly block a legitimate draft→active transition on an experiment that already has children.
- **Activation-readiness checks.** [experiments/readiness.py](experiments/readiness.py) `readiness_problems(experiment)` (list of human-readable gaps; empty = ready) + `is_walkable(experiment)` (bool). `Experiment.clean()` blocks becoming `ACTIVE` unless `readiness_problems` is empty, and blocks entering `TEST` from draft unless `is_walkable`. **Both gates only run via `full_clean()`** — direct `save(update_fields=["state"])` (factories, the admin activate view) bypasses them, so the admin `activate_view` re-checks readiness itself (it flips state with `update_fields`). Surfaced on the studio overview and the admin activate page (the Activate button disables when problems exist). Checks: ≥1 condition, ≥1 active stimulus, ≥1 stimulus-section question, non-empty consent text, `stimuli_per_participant ≤ available` (standard mode only), pairwise needs ≥2 stimuli, and a screening rule needs screening questions.
- **Preview / pilot separation.** `ParticipantSession.is_preview` is stamped True at creation (`survey/views.py::_create_session`) when `experiment.state == TEST`. Every per-experiment stat ([experiments/stats.py](experiments/stats.py)), every CSV export ([experiments/csv_exports.py](experiments/csv_exports.py)), and `global_summary` filter `is_preview=False`, so a rehearsal never contaminates the dataset. Activating from TEST: the admin activate view purges preview data, or — when "keep test data" is chosen — promotes those sessions into the real dataset (`is_preview=False`).
- **Per-question analysis + inferential tests.** [experiments/analysis.py](experiments/analysis.py) `analyse_question` / `experiment_question_analysis` return a typed `QuestionResult` (kind ∈ distribution/numeric/matrix/ranking/text/other) for **every** question type over real (submitted, non-preview) sessions; `_summarise(question, values)` is the pure dispatch so `segmented_question_analysis(experiment, segment_by)` (device/country/condition/cohort, the last bucketed by ISO submission week) reuses it. [experiments/stats_tests.py](experiments/stats_tests.py) provides ready-to-use across-condition tests with **no scipy dependency** — hand-rolled regularized incomplete beta/gamma (`betainc`/`_gammp`) back `t_sf_two_sided`/`f_sf`/`chi2_sf`; `compare_conditions(experiment, question)` runs one-way ANOVA (numeric/rating/likert) or chi-square (choice) on per-condition groups (per-stimulus questions only). scipy/pandas live in the optional `analysis` extra (not installed by default), so analysis code must stay scipy-free on the always-installed path. Surfaced read-only on the studio overview (`studio/templates/studio/_question_results.html` + `_result_body.html`), with a `?segment=device|country|condition|cohort` selector.
- **Response times, power, cross-experiment, event log.** `Response.elapsed_ms` is the server-measured page dwell time: `_base_context` stamps a hidden `_t0` (epoch ms) into every question form and `_page_elapsed_ms(request)` reads it in `_collect_answers`/`_collect_pairwise_answers` (server clock both ends; negative/>6h deltas dropped); `analyse_question` reports the per-question median. [experiments/power.py](experiments/power.py) is pure-stdlib power analysis (`norm_cdf`/`norm_ppf` Acklam, `required_n_per_group`/`achieved_power`/`cohens_d`); `studio:power_analysis` is a calculator + a pilot-data estimator. `studio:compare` tables key metrics across `_visible_experiments(user)`. `survey.SurveyEvent` is an append-only, PII-free flow log (`started`/`page_submit`/`screened_out`/`completed`) written via the best-effort `survey/views.py::_log_event` (must never break the flow); withdrawal deletes a session's events; exposed via an owner-scoped admin changelist and `studio:events_csv`.
- **Compliance & governance.** `Experiment` carries compliance metadata (`irb_number`, `legal_basis` ∈ GDPR bases, `data_contact`, `retention_days`) + a derived `consent_version` property (sha256 prefix of `consent_text`); `ParticipantSession.consent_version` is stamped at consent so data stays tied to the wording agreed to. `accounts.AuditEvent` (append-only, mirrors `AccessEvent`) logs edit/export/activate/purge/delete via `accounts/services.py::record_audit` — instrumented on studio exports, `study_build_save`, `ExperimentAdmin.save_model`, and the activate/purge view. `purge_expired_data` (management command) deletes sessions past each study's `retention_days` (submitted_at for completed, started_at for abandoned; `--dry-run`), audited. `Question.contains_pii` redacts free-text in the answers/demographics CSV unless `?include_pii=1`. `studio:dsr` (data-subject requests) finds a participant's sessions across `_visible_experiments(user)` by `participant_uid`/`external_id` and exports (JSON) or erases them (reusing `survey/views.py::_withdraw_data`, only for studies the user `can_manage`), all audited. scipy stays off the always-installed path; compliance code is pure-stdlib.
- **One-click cloning.** [experiments/cloning.py](experiments/cloning.py) `clone_experiment(experiment, *, owner, name=None)` deep-copies into a fresh DRAFT owned by `owner`: a generic `_meta.concrete_fields` copy (skipping id/slug/owner/state/counters/`follows`/`name`), raw media **bytes** re-saved for audio/image/video stimuli and pairwise prompts (not a shared file path), and `visible_if` / `eligibility_rule` question references remapped via an old→new question-id map. Unlike the lossy ZIP import/export ([experiments/imports.py](experiments/imports.py) drops `visible_if`/`attention_expected`), the clone is faithful. Callers grant the OWNER `Membership` (studio `study_clone` view / admin "Duplicate" action) — `cloning.py` stays free of an `accounts` import.
- **Per-study branding.** `Experiment.brand_primary_color` (regex-validated hex), `brand_logo` (`ImageField`, `upload_to="branding/"`), `brand_custom_css` (trusted raw CSS, same trust model as consent HTML). [templates/base.html](templates/base.html) injects the color as Pico `--pico-primary*` vars + the progress-bar fill, renders the logo in the survey header, and appends the custom CSS — all guarded by `{% if experiment.brand_* %}` so unbranded studies are byte-identical. Authored via the admin "Branding" fieldset.
- **Question bank.** `experiments.QuestionTemplate` is an experiment-independent question blueprint (`owner` FK, `owner=NULL` = shared/global). `from_question(q, *, owner)` / `build_question(experiment, *, sort_order)` round-trip every authored field **except** `visible_if` (which references sibling question ids, meaningless outside its experiment). Admin: an owner-scoped `QuestionTemplateAdmin` changelist (`Q(owner=user) | Q(owner__isnull=True)`, superuser sees all), a "Save selected questions to my question bank" action on `QuestionAdmin`, and a per-experiment, draft-only, `can_edit`-gated `add_from_bank_view` (mounted in `get_urls()` as `admin:experiments_experiment_add_from_bank`).
- **Single `Question` model with `type` + `section` + `page_break_before` + JSONField `config`.** `type ∈ {rating, choice, text, likert, numeric, matrix, ranking}` determines the widget and validation (`_validate_question_config` in [experiments/models.py](experiments/models.py); composite types — matrix/ranking — are read from multiple POST keys via `survey/views.py::_read_one`); `section ∈ {stimulus, demographic, screening}` decides whether the question runs per-stimulus, once at the end, or once before the task (screening, gated by `Experiment.eligibility_rule`). `page_break_before` is the author-controlled PsyToolkit page-break: a true value starts a new page before that question. Rating `min`/`max`/`step` are admin-configurable and rating may carry optional `min_label`/`max_label` strings for PsyToolkit-style scale anchors.
- **Single `Stimulus` model with a `kind` discriminator.** `kind ∈ {audio, image, text, video, html, embed}`: `audio` requires the `audio` `FileField` (extension + size validated via [experiments/validators.py](experiments/validators.py) audio helpers; SHA-256 + mutagen duration auto-computed on save); `image` requires the `image` `FileField` (extension + size validated via the image helpers; SHA-256 auto-computed on save, no duration); `text` requires a non-empty `text_body` (no file, no hash, no duration); `video` mirrors `audio` (own `FileField` + checksum + mutagen duration + watch-time tracking via the same `data-listen-endpoint` JS); `html` reuses `text_body`, rendered as raw researcher-authored HTML (same trust model as the Markdown consent/instructions text); `embed` requires an `embed_url` shown in a sandboxed iframe. `Stimulus.clean()` enforces these rules and rejects cross-kind contamination via a single field-ownership matrix in `_validate_kind_fields`. `save()` hashes whichever media field exists via `_media_field()`, and probes duration for time-based media (`audio`, `video`).
- **Pluggable assignment strategies.** `StrategyBase.select(experiment, n, counts, rng, participant_index=None)` in [experiments/assignment.py](experiments/assignment.py) returns an ordered `list[Stimulus]`; it may query stimuli/conditions but never touches `ParticipantSession`/`StimulusAssignment` (the per-stimulus `counts` and the `participant_index` ordinal are supplied by `survey/views.py::_build_assignments`). Strategies register in `_REGISTRY`, looked up by name from `Experiment.assignment_strategy` (the admin dropdown lists `available_strategies()`). Ship strategies: `balanced_random` (least-used condition, then least-used stimulus), `block_random` (balanced set ordered into randomized one-per-condition blocks), `counterbalanced` (block order rotated systematically by `participant_index`), and `between_subject` (each participant sees a single condition, round-robin by `participant_index`; the chosen condition is recorded on `ParticipantSession.assigned_condition`).
- **Pluggable question-type components (plugin system).** [experiments/components.py](experiments/components.py) generalizes the assignment-strategy pattern: a `QuestionComponent` base (`type`, `label`, `validate_config`, `render(question, *, post=None)`, `read_answer(post, question) -> (answered, value, error)`), a `_REGISTRY`, `register_question_component` / `get_question_component` / `is_question_component` / `available_question_components`, and a `@question_component` class decorator. `ExperimentsConfig.ready()` imports the registry and `autodiscover_modules("question_components")` so any app registers by dropping one module. **Additive, not a refactor:** built-in types keep their hard-coded paths; a component adds a *new* `Question.type` value. Dispatch points fall back to the registry for unrecognized types — `Question.clean_fields` (accept the plugin type past the static `Type.choices`), `_validate_question_config` (call the component's `validate_config`), `survey/views.py::_read_one` (call `read_answer`), and `survey/_question.html`'s `{% else %}` → `{% question_widget q %}` ([experiments/templatetags/component_tags.py](experiments/templatetags/component_tags.py), passes `request.POST` on a 400 re-render so the widget repopulates). Admin authoring: `QuestionAdminForm` adds registered components to the type dropdown and a raw-JSON `plugin_config` field (validated via the component). Ships one worked example, `ConstantSumComponent` (`constant_sum`). A component key must be ≤16 chars (the `Question.type` `max_length`) and not shadow a built-in.
- **Participant flow is a paged state machine.** [survey/flow.py](survey/flow.py) holds `STEP_URL_NAMES`, `required_step_url()`, plus two PsyToolkit helpers: `paginate_questions(questions)` groups an ordered question sequence into `list[list[Question]]` pages (the first question always starts a new page; subsequent questions start a new page iff `page_break_before=True`); `progress_percent(session, ...)` returns 0..100 across the full survey (consent + instructions + all stimulus pages + all demographic pages + thanks). `ParticipantSession` carries three cursors — `current_assignment_index`, `current_page_index`, `demographic_page_index` — advanced by each page POST in [survey/views.py](survey/views.py) `_save_page_answers()` / `demographics()`. Every view calls `_expect_step(session, step)` and redirects out-of-order navigation. Non-active experiments at `/s/<slug>/` render `survey/unavailable.html`, never 404. Question order is randomized once per participant (`random.Random(str(session.id))`) and cached on the in-memory session instance for refresh stability.
- **Conditional display (skip logic).** `Question.visible_if` (JSONField) holds an optional rule — `{"question": id, "op": ..., "value": ...}` or `{"all"|"any": [clauses]}` — validated by `_validate_visible_if` in [experiments/models.py](experiments/models.py) (the referenced question must be in the **same section** with a strictly **lower `sort_order`**). The pure engine is [experiments/branching.py](experiments/branching.py) (`evaluate_condition`/`is_visible`), placed in `experiments` so `survey` imports it (never the reverse). The flow ([survey/views.py](survey/views.py)) hides questions whose rule fails against answers already stored for the current stimulus / demographic section, and `_next_renderable_stimulus_page` / `_next_renderable_demographic_page` skip fully-hidden pages **internally** (one redirect, not one per page — avoids redirect loops). Per-session question shuffle is disabled when any stimulus question has a `visible_if` so controllers always precede dependents. Cross-page branching is fully server-side (no JS); [survey/static/survey/js/branching.js](survey/static/survey/js/branching.js) adds same-page live reveal as progressive enhancement — the server stays authoritative, never requiring or storing a hidden question.
- **Screening / eligibility.** Questions with `section=screening` run once after consent and before the task. `Experiment.eligibility_rule` (same DSL as `visible_if`, validated to reference only screening questions) is evaluated by `survey/views.py::_finish_screening`; failing participants get `last_step=SCREENED_OUT` + `screened_out_at`, their cookie is cleared, and they're excluded from results (no `submitted_at`). Reuses the branching engine (`evaluate_condition`) and the paged-flow `_next_renderable_*` helpers. `consent` routes to `survey:screening` when the experiment has screening questions.
- **Quality flags.** [survey/flagging.py](survey/flagging.py) `compute_flags(session)` runs once at `_finish_session` and stores `ParticipantSession.failed_attention_checks` + `flags` (a list drawn from `failed_attention`/`speeder`/`straight_lining`/`duplicate`). Attention checks are `Question.attention_expected` (a stored answer ≠ expected ⇒ fail); speeder compares consent→submit elapsed against `Experiment.min_completion_seconds`; straight-lining = an identical answer to every rating/likert stimulus question; duplicate = another completed session shares this participant's `participant_uid` (a long-lived `webeval_pid` cookie set at consent — `Experiment.one_submission_per_participant` blocks a second completion outright). The `csv_exports` builders accept `exclude_flagged` (drops sessions whose `flags` is non-empty), wired via `?exclude_flagged=1` on the studio export links; the participant-session admin shows the flags and a Flagged filter.
- **Completion codes & compensation.** `Experiment.completion_code_mode` (`none`/`fixed`/`unique`) sets the code shown on the thanks page — `unique` codes are generated in `_finish_session` and stashed in the Django session (the survey cookie is already cleared by then). `Experiment.external_id_param` captures a platform id (e.g. `PROLIFIC_PID`) from the consent URL into `ParticipantSession.external_id`. `ParticipantSession.compensation_status` (pending/approved/paid/rejected) is the one editable field on the otherwise read-only session admin; `experiments/csv_exports.py::completion_codes_csv_response` exports code/external-id/status for reconciliation (linked from the studio overview).
- **Longitudinal / multi-phase studies.** `Experiment.follows` (self-FK, `on_delete=SET_NULL`, reverse `next_phases`) chains studies into ordered phases a participant returns to over time; `Experiment.phase_gap_hours` enforces a minimum spacing before a later phase opens. `_validate_phase_chain` (in [experiments/models.py](experiments/models.py), called from `clean()`) requires `collect_participant_code` on **both** the follow-up and its predecessor (the participant code is the cross-visit identity key, reused as `participant_uid`), rejects self-follow, and walks the `follows` chain to reject cycles. The gate is server-side at consent: `survey/views.py::_longitudinal_block` (run after the participant-code + one-submission checks, only when `follows_id` is set) renders `survey/already_completed.html` if this phase is already done, or `survey/phase_locked.html` with `reason="predecessor"` (predecessor not completed under that code) / `reason="too_early"` (gap not yet elapsed, with `opens_at`). On completion the thanks page advertises the next phase: `_finish_session` stashes `webeval:uid:<slug>` (the participant code) in the Django session, and `thanks` builds `next_phase` (name + absolute consent URL + the code to reuse + `opens_at`) from `experiment.next_phases`. Authored via the admin "Longitudinal (multi-phase)" fieldset (`autocomplete_fields = ("follows",)`) and surfaced read-only on the studio overview.
- **Withdrawal & data deletion.** `/s/<slug>/withdraw/<token>/` (token = the session's `resume_token`) lets a participant erase their data at any time; `survey/views.py::_withdraw_data` deletes the `Response`/`StimulusAssignment`/`PairAssignment` rows and leaves an anonymised tombstone (`withdrawn_at`, `last_step=WITHDRAWN`, with PII / `submitted_at` / `resume_token` cleared) so withdrawn sessions fall out of exports and stats. A "Withdraw & delete my data" link is rendered on every in-progress page and on the thanks page (via a token stashed in the Django session at completion).
- **Private access, bot protection & participant codes.** `Experiment.access_mode` (`public`/`code`/`invite`) gates the survey via `survey/views.py::_access_gate` at the top of `consent`: `code` checks `Experiment.access_code` (entered on `/s/<slug>/access/` or passed as `?code=`); `invite` requires a single-use `experiments.ParticipantInvite` token (`?invite=`, consumed at session creation), bulk-generated by an admin action. Granted state is stashed in the Django session. `Experiment.bot_protection` adds a consent honeypot (`hp_url`) that silently blocks session creation when filled. `Experiment.collect_participant_code` asks for a stable code at consent that becomes the session's `participant_uid` — a lightweight cross-device "account" enabling cross-device duplicate detection and return visits.
- **Completion is the last POST.** The last page of the demographics section (or of the stimuli section, if there are no demographic questions) calls `_finish_session()` which stamps `submitted_at`, flips `last_step = DONE`, and clears the session cookie. There is no separate "review & submit" step.
- **CSV exports exclude abandoned sessions.** Both [experiments/csv_exports.py](experiments/csv_exports.py) helpers filter on `session__submitted_at__isnull=False`. The long-format answers CSV additionally filters `stimulus__isnull=False` so demographic rows don't leak in.
- **Minimal JS.** Participant-facing pages stay (almost) JS-free: the only hand-written participant modules are [survey/static/survey/js/audio-tracker.js](survey/static/survey/js/audio-tracker.js) (accumulates playback time on `timeupdate`, guarded against seek deltas, reports via `navigator.sendBeacon` with a `fetch` fallback; no-ops without a `#stimulus-audio`/video element) and [survey/static/survey/js/branching.js](survey/static/survey/js/branching.js) (same-page skip-logic reveal, pure progressive enhancement — the server stays authoritative). Everything else participant-facing is server-rendered; charts are matplotlib-SVG and the rating widget is a native `<input type="range">` + `<output>`. The **one richer JS module is the researcher-only drag-&-drop question builder** [studio/static/studio/js/builder.js](studio/static/studio/js/builder.js) — vanilla, no build step, and still server-authoritative (it POSTs the question set as JSON to `studio:study_build_save`, which validates + persists). It is deliberately confined to the studio (researchers), never the participant flow.
- **Drag-&-drop question builder.** [studio/views.py](studio/views.py) `study_build` (GET, `can_edit`-gated; read-only off-draft) renders a palette of question types — built-ins from `Question.Type.choices` plus every registered plugin via `available_question_components()` (each with a `default_config()`) — embedded with `json_script`, hydrated by `builder.js`. `study_build_save` (POST JSON `{questions:[…]}`) reconciles the set in one transaction: upsert by `id`, `sort_order` = array index, **`full_clean()` each** (so config + plugin + `visible_if` rules are enforced), delete the rows no longer present, then return the saved ids in order so the client adopts them (a re-save updates in place). Friendly config editors ship for rating/choice/text/likert/numeric; other types (matrix/ranking/plugins) use a raw-JSON config field. Questions are now authorable by **non-staff editors** in the studio; conditions/stimuli still go through the admin.

- **Access is owner + role scoped via one helper.** [accounts/permissions.py](accounts/permissions.py) (`role_for`, `can_view`/`can_edit`/`can_manage`, `visible_experiment_ids`) is the single source of truth, consumed by the studio dashboard, the admin (`OwnerScopedAdminMixin` on every experiment/survey `ModelAdmin` + object checks in the `ExperimentAdmin.get_urls()` per-study views), and the REST API ([experiments/api.py](experiments/api.py)). `Experiment.owner` is the authoritative pointer (`on_delete=PROTECT`); the owner also holds an `OWNER` `Membership` so a check is one query. Superusers bypass. **Gradual-rollout rule:** an experiment with `owner IS NULL` (legacy / pre-RBAC) stays fully accessible to `is_staff` users; once it has an owner it is strictly scoped — so introducing ownership was non-breaking. Collaborator/ownership mutations go through [accounts/services.py](accounts/services.py) (each appends an `AccessEvent`) and are allowed in **any** state — they never touch the `_ensure_draft` child-edit lock.

### Data model summary

```
Experiment ─── Condition ─── Stimulus {kind: audio|image|text|video|html|embed,
    │                            audio?/image?/video?, text_body?, embed_url?}
    │
    └── Question (section: stimulus|demographic,
    │             type: rating|choice|text|likert|numeric|matrix|ranking,
    │             page_break_before: bool, visible_if: skip-logic rule)
    │
    └── ParticipantSession ─── StimulusAssignment (listen_duration_ms)
           │  (current_assignment_index, current_page_index,
           │   demographic_page_index)
           │
           └── Response (stimulus nullable; JSON-encoded answer)
```

`ParticipantSession.last_step` drives the top-level flow state machine (consent → instructions → stimuli → demographics → done). Within STIMULI and DEMOGRAPHICS the three integer cursors on the session drive the per-page PsyToolkit pagination. `Response.stimulus` is nullable because demographic answers aren't tied to a clip.

Access control layers on top: `Experiment.owner` FKs the owning `User`, and the `accounts` app adds `Profile` (1:1 `User`), `Membership` (user × experiment → role), `Invitation` (tokenised), and the append-only `AccessEvent`.

## Configuration

Settings are env-driven via `django-environ` ([core/settings.py](core/settings.py)). A committed `.env.example` lists every variable; `.env` is gitignored. Notable env vars:

- `SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS`, `DATABASE_URL` — standard Django.
- `GEOIP_PATH` — path to a MaxMind GeoLite2-Country `.mmdb`. Optional: if the file is missing, `survey/metadata.py` returns an empty `country_code` without raising.
- `STIMULUS_MAX_UPLOAD_BYTES`, `STIMULUS_ALLOWED_EXTENSIONS`, `STIMULUS_ALLOWED_MIME_TYPES` — audio upload validation.
- `STIMULUS_MAX_IMAGE_UPLOAD_BYTES`, `STIMULUS_ALLOWED_IMAGE_EXTENSIONS` — image upload validation (kind=image).

Database is SQLite by default (README pins this); swap only if asked.

## Testing conventions

- Factories live in [experiments/tests/factories.py](experiments/tests/factories.py) — `ExperimentFactory`, `ConditionFactory`, `StimulusFactory` (kind=audio, ships a minimal fake MP3 blob), `ImageStimulusFactory` (kind=image, synthesises a PNG via Pillow), `TextStimulusFactory` (kind=text), `RatingQuestionFactory`, `ChoiceQuestionFactory`, `TextQuestionFactory`.
- Identity/access factories (`UserFactory`, `StaffUserFactory`, `SuperUserFactory`, `MembershipFactory`, `InvitationFactory`) live in [accounts/tests/factories.py](accounts/tests/factories.py). Pass `ExperimentFactory(owner=user)` to get an owned study — owner alone grants access, so no `Membership` row is needed for the permission check.
- Factories produce **draft** experiments; flip `state = Experiment.State.ACTIVE` and `save(update_fields=["state"])` before hitting participant views that require `require_active=True`.
- End-to-end test at [tests/test_end_to_end.py](tests/test_end_to_end.py) runs one participant through the full flow and verifies the admin details page + CSV see the data. Use this as the template for any new cross-app integration test.
- Admin-embedded stats, CSV exports, chart endpoint, and the purge management command are covered in [tests/test_admin_stats.py](tests/test_admin_stats.py). The fixtures in that file are also a ready-made way to populate an experiment with a handful of completed + abandoned sessions if you need one.
- Browser-driven admin CRUD tests live in [tests/test_admin_selenium.py](tests/test_admin_selenium.py). They spin up a headless Firefox (fallback: Chromium) via `pytest-django`'s `live_server` fixture. Snap-confined browsers can only read files under `$HOME` and can't see dotdirs, so the `browser_tmpdir` fixture writes stimulus uploads into `~/webeval-selenium-tmp/` rather than `/tmp`. Override the browser binary with `FIREFOX_BIN` / `CHROME_BIN` env vars; the whole module auto-skips if no driver starts.
- The selenium helpers (`_login`, `_click_submit`) scope their XPath to the form carrying the expected `name` attribute (e.g. `//form[.//input[@name='username']]`) rather than picking the first `button[type="submit"]` on the page. This is deliberate: Unfold's themed pages carry extra forms (theme toggle, object-action dropdowns) whose submit controls would otherwise shadow the intended target. Also note the `?next=/admin/` passed to the login URL — Unfold's login template doesn't inject the hidden `next` field, so without it Django bounces post-login to `LOGIN_REDIRECT_URL` (now `/studio/`, the researcher dashboard).
